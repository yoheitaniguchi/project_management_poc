## 6. 展開に向けて残る課題

PoCの範囲で割り切ったこと（CLAUDE.md の決まり・人間の判断）を、展開するときの課題として挙げる。PoC期間中に分かったことは追記する。

### 技術構成
- バックエンドとDBを持たず、データは利用者のブラウザ（localStorage）とPCのJSONにだけある。複数人で同じ案件を見ることや、複数案件の横断はできない
- GitHub Pages の配信先は姉妹リポジトリと同じオリジンのため、そのページからこの保存データを読み書きできる（PoCではリスクを受け入れた。CLAUDE.md 6.1）
- 正式な記録は、毎週人間が書き出すJSONに頼っている。書き出し忘れやブラウザのデータ消去で記録を失うおそれがある

### 権限
- 認証が無く、操作者・承認者は自己申告である（CLAUDE.md 4章）
- 実績工数の個人別表示の権限は、画面の表示を制御するだけで、JSONや開発者ツールからは全員の実績を読める。展開するときは、認証と、書き出すデータを絞る仕組みが要る（`docs/security/reports/review-20261025-0110.md` SEC-001）

### 監査
- 監査ログ・ベースライン・スナップショットの「変更しない」は、ツールの操作と JSON の読み込み時の検査で守っている。保存データが空のブラウザで、値をそろえて書き換えたJSONを読み込むと通ってしまう（`docs/security/reports/review-20261022-2320.md` SEC-003）
- スナップショットの作成は監査ログに記録しない（人間の判断 2026-10-22）

### Asana 連携
- Asana のCSVでは実績がタスクごとの累計で、作業日ごとの明細が無い。差分を「CSVを書き出した日」の実績にするので、週の中の作業日は分からない（人間の判断 2026-10-25）
- 取り込んだ実績は画面から取り消せない（CR-004 保留。誤取込のときはJSONを手で直す）
- Asana の取込と手入力のCSVの両方を使うと、二重に数えるおそれがある（警告だけを出す）

### 運用体制
- 利用者1名（PM兼監理者）で、承認・レビュー・受け入れを同じ人が行っている。展開するときは、承認者と作業者を分ける必要がある
- 見積基準は「仮」の値で始めた。PoCの実績を見て見直す（CLAUDE.md 4章）
- 要対応の閾値（仮に5ポイント）は、PoCの結果を見て見直す（CLAUDE.md 5章）。見直した値：（未記入）
